# Visual Studio extensibility routes

Reviewed 2026-09-07 against Microsoft documentation and samples.

| Concern | VisualStudio.Extensibility out-of-process | Established VSSDK/VSIX |
| --- | --- | --- |
| Supported IDE | Visual Studio 2022 17.9+ generally; the pinned 17.14 SDK targets 17.14+ | Visual Studio 2022; older LSP client support also exists |
| Runtime | .NET 8 Windows process outside `devenv.exe` | Usually .NET Framework/in-process VSPackage or MEF component |
| Workload | Visual Studio extension development | Visual Studio extension development / Visual Studio SDK |
| LSP hook | `LanguageServerProvider`, stdio duplex pipe, initialization options, initialization result | `ILanguageClient`/MEF, broader custom-message hooks |
| Commands | supported | supported |
| Tool windows | supported through asynchronous Remote UI | mature WPF/VSSDK surface |
| Deployment | Visual Studio-specific VSIX generated by the SDK | Visual Studio-specific VSIX |
| Failure isolation | adapter remains outside the IDE process | adapter failures can affect the IDE process |
| Limitations | LSP and settings APIs are still marked preview; no documented arbitrary client request hook; Remote UI has no code-behind or custom controls | larger API and threading surface; in-process reliability risk; more complex packaging |

## Choice

Adopt the out-of-process route for the minimum diagnostic adapter. It directly
supports a native stdio server, initialization options, commands, settings,
ordinary diagnostics, and server start/failure callbacks while preserving IDE
isolation. Defer the report tool window and custom `harnessLens/*` request client
until the API supports that transport or a separate decision justifies a small
in-process bridge.

The traditional route was rejected for this slice because diagnostics and basic
lifecycle do not require its broader in-process surface. It remains a fallback
only for a confirmed API gap.

## Licensing and attribution

Visual Studio 2026 uses API-version-based compatibility with 2022 extensions.
The candidate declares API 17.14+ and AMD64 only because its native server is x64.
Host testing, rather than the manifest alone, determines supported compatibility.
See [Microsoft's compatibility model](https://learn.microsoft.com/en-us/visualstudio/extensibility/migration/extension-compatibility).

This implementation is original MPL-2.0 code. Microsoft's VSExtensibility sample
repository is MIT-licensed and was used to confirm API shapes. NuGet dependencies
are Microsoft-published packages; their package license files and notices must be
captured in the release SBOM/notices audit before publication.
